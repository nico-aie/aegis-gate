# WAF Hackathon 2026 — v2.5 → v2.6 Change Analysis

Comparison of the updated Candidate Briefing (`EN_present`) and Interop Contract (`EN_waf_interop_contract`) from **v2.5 (2026‑05‑17)** to **v2.6 (2026‑06‑10)**.

---

## 1. Executive Summary

v2.6 is a **structural and scoring overhaul of the competition format** (in the briefing) plus a **specification‑tightening release** (in the contract). Nothing that previously passed is silently broken, but two changes can actively change a run's outcome and require code/behaviour action:

- **Unsupported‑item handling is reversed** — `200 OK` is now the safe path; `400/422` will now *abort the benchmark run*. (Contract §2.5/§2.8)
- **Basic rate‑limit and basic proof‑of‑work challenge are now mandatory and must be self‑built**, with required formats. (Contract §4)

The biggest *strategic* shift is in the briefing: Round 2 is now two‑phase with a manual enterprise‑feature Dashboard check that can eliminate you even after you pass the automated benchmark, and Round 1 bonus points no longer count.

## 2. Candidate Briefing (`EN_present`) — v2.5 → v2.6

### 2.1 Round renaming & restructure

| | v2.5 | v2.6 |
|---|---|---|
| Round 2 name | Automated Benchmark & Adversarial Evaluation | **Enterprise Functional & Benchmark Evaluation** |
| Round 2 structure | Single automated benchmark | **Two phases**: Phase 1 automated benchmark → Phase 2 manual Dashboard check |
| Round 3 name | Performance & Load Resilience | **DDoS / Red Team Attack Battle** |

### 2.2 Scoring model (the most consequential briefing change)

| Item | v2.5 | v2.6 |
|---|---|---|
| Round 2 weight | 65% | **70%** |
| Round 3 weight | 35% | **30%** |
| Round 1 bonus points | Added directly to total score | **No longer carried forward**; Round 1 criteria re‑checked in Round 2 Phase 2 |
| 70% benchmark threshold | Gate into Round 3 | Gate from **Phase 1 → Phase 2** only |
| Advancement to Round 3 | Anyone ≥70% in R2 | **Top 6** by combined Phase 1 + Phase 2 |
| Winners | (not specified as top‑N) | **Top 3** |

### 2.3 New rules introduced in v2.6

- **Phase 2 can eliminate you even if Phase 1 passed.** Passing 70% of the automated benchmark no longer guarantees advancement. A team missing core enterprise‑WAF features (reliable rule management, hot‑reload, real‑time event/metric display, audit‑log accuracy, access control, detection coverage, mode toggling, resilience), or whose Dashboard claims features that don't actually drive WAF behaviour, can be cut at Phase 2.
- **Submission readiness clause.** The OC evaluates the WAF *exactly as submitted* — no resetting, restarting, rebuilding, or reconfiguring by the OC. A WAF that doesn't start or is misconfigured at submission is scored accordingly.
- **Benchmark deployment flexibility.** The benchmark tool may be deployed onto any team's WAF‑server depending on the scenario (cross‑team, isolation, shared infra).
- **Dashboard operability under load is mandatory in Round 3.** The OC must monitor the Dashboard during the Attack Battle to confirm displayed events/metrics/state accurately reflect real traffic and that it stays smooth under load.

### 2.4 Briefing's own delta list (v2.6 §5)

The v2.6 briefing summarizes its changes vs v2.5 as: Round 2 two‑phase restructure; Round 1 bonus no longer carries forward; 70/30 weights; top 6 advance / top 3 win; Phase 2 elimination; Round 3 renamed with Dashboard operability requirement; mandatory Dashboard monitoring in Round 3; submission‑readiness clause.

## 3. Interop Contract (`EN_waf_interop_contract`) — v2.5 → v2.6

### 3.1 Action‑required changes (can change a run's result)

**§2.5 / §2.8 — Unsupported items: recommendation REVERSED.**
- v2.5: WAF MUST either (1) return `400/422` with an `unsupported` list, **or** (2) return success with the unsupported items listed.
- v2.6: **`200 OK` with a machine‑readable `unsupported` list is the recommended, benchmark‑safe path.** Returning `400/422` for a partially‑supported scope (e.g. `features`/`policies` when only `all` is native) is now explicitly **punitive — the benchmark run is aborted after the current test.** If your WAF currently returns 4xx for partial scopes, change it.

**§4 — Rate‑limit and challenge now fully specified, basic versions MANDATORY.**
- v2.5 specified only the *challenge* response format (Format A JSON / Format B HTML) and the self‑built/no‑third‑party rule.
- v2.6 adds an explicit **basic (mandatory) vs advanced (optional)** split for **both** rate‑limit and challenge:
  - **Basic rate‑limit (mandatory):** self‑built, no third‑party limiter. Required logic: per‑client count in a time window → compare threshold → `429` with `X-WAF-Action: rate_limit`. Must include `Retry-After` header and/or `retry_after_seconds` body field. Full example response provided.
  - **Basic PoW challenge (mandatory):** self‑built token+difficulty, client finds nonce, WAF verifies. The HTML example is expanded to a complete SHA‑256 JS solver. Submission flow unchanged (`POST <submit_url>` with `{challenge_token, nonce}` → `200` + session token).
  - Advanced versions optional but must still be self‑built; the basic version must remain functional/parseable.

### 3.2 Clarifications & tightening (behaviour should already comply, but verify)

- **§2.1 — Control POST endpoints must accept a body.** Benchmark sends `{}` for `reset_state`/`flush_cache`; the WAF MUST NOT reject a request solely because a body is present.
- **§2.2 — Auth secret required on *every* method.** `X-Benchmark-Secret` is now explicitly required on `GET`, `POST`, `PUT`, `DELETE` (v2.5 said only "on every request" generically).
- **§2.3 — `active` object is informative only.** Omitting it is not a failure; the tool reads it for display. Reaffirms `200 OK` (not `ok: true`) as the primary success signal.
- **§2.4 — Runtime reset semantics expanded.** Explicit "return to a **fresh runtime state as if just started**." Critically: `reset_state` **MUST NOT revert feature/policy settings** — whether set at runtime via `set_profile` or loaded from `waf.yaml`/`waf.toml`. Only temporary per‑request/per‑session data is cleared.
- **§2.5 — Feature toggleability (new subsection).** All features SHOULD appear in `/capabilities` for transparency, **including hardcoded ones**. Hardcoded features that can't respond to `set_profile` SHOULD be reported `toggleable: false`; if a feature claims `toggleable: true` but doesn't respond, the fault is the team's. Adds explicit "Override key conventions" (feature‑level key vs `feature.policy` dot notation) and "Unsupported items" subsections.
- **§2.6 — Cache flush with no cache.** v2.5: "MAY return a clear not‑supported response." v2.6: SHOULD return **`501 Not Implemented` or `200 OK`** — `404` is now treated as an **endpoint failure.**
- **§1 / §11b — Dashboard evaluation aligned to the new rounds.** Dashboard is judged manually in **Round 2 Phase 2** and monitored during the **Attack Battle (Round 3)**; monitoring under load is now mandatory. A note distinguishes benchmarker `set_profile` API calls from Dashboard‑initiated toggles during the manual Phase 2 check. Benchmark‑deployment‑flexibility language added to match the briefing.
- **§13 — Minimum Viable WAF Checklist** gains items for `capabilities` accuracy and feature‑toggle consistency (toggleable:true must actually respond; hardcoded features reported toggleable:false or documented).

### 3.3 Contract's own delta list (v2.6 §12)

The contract's §12 enumerates the v2.6 changes: §2.4 reset semantics; §2.5 feature toggleability; §4 rate‑limit + challenge spec; §13 checklist updates; §2.6 flush‑cache no‑cache codes; §2.8 unsupported‑items fix; §11b deployment flexibility + phase alignment + mandatory Dashboard monitoring.

> **Note / minor inconsistency:** the §12 delta references "§2.8 Unsupported items," but in the body the unsupported‑items content sits under **§2.5**. There is no standalone §2.8 heading. Worth flagging to the committee.

## 4. What This Means For Implementation (Priority Order)

1. **Check unsupported‑scope handling.** If `set_profile` returns `400/422` for `features`/`policies` while you only support `all`, switch to `200 OK` + `unsupported` list, or you risk an aborted run.
2. **Confirm a basic self‑built rate‑limiter and PoW challenge exist** and match the §4 formats (including `Retry-After` / `retry_after_seconds`). Remove any third‑party limiter/CAPTCHA dependency in the basic path.
3. **Verify `flush_cache` returns 501/200 (never 404)** when caching is absent.
4. **Verify `reset_state` does not reset feature/policy modes** (config or `set_profile`‑set) — only ephemeral state.
5. **Audit `/capabilities`** so every feature is listed and hardcoded ones report `toggleable: false`.
6. **Confirm `X-Benchmark-Secret` is enforced on all methods** and POST control endpoints tolerate a body.
7. **Strategically: invest in the Dashboard / enterprise feature set.** Round 2 Phase 2 and Round 3 both now hinge on it, and it can eliminate you regardless of benchmark score. Ensure the WAF is submission‑ready (starts cleanly, correctly configured) since the OC won't fix it.
