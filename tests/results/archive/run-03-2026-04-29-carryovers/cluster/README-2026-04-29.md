## Cluster smoke run

Full log: [`run-2026-04-29.log`](./run-2026-04-29.log).

### Test 01 — shared-counter (B1-T1 + B1-T2) — **PASS**

Sent 10 requests to node A (`http://127.0.0.1:8080`), then 10 to
node B (`http://127.0.0.1:8090`), against a shared
`redis://127.0.0.1:6379`. Node B's RiskTracker view of
`127.0.0.1` reported `idle_seconds=0` — proves the counter is
shared across nodes via the Redis backend; without B1-T1's
`RedisBackend` + B1-T2's backend selection, node B would see
no activity from node A's traffic.

Prometheus consume metrics on both nodes were 0 — that metric
isn't instrumented for plain `/` traffic in this build, so the
RiskTracker idle check is the load-bearing assertion.

### Test 02 — leader-failover (B1-T3) — **SKIP**

The script polls `GET /api/cluster/leader` for an
`is_leader: true|false` field. The current build exposes
`/api/cluster` (returns `{"peers":[]}`) but **not**
`/api/cluster/leader`. Both nodes returned 404; the script
correctly skipped:

```
SKIP: leader-state admin surface not exposed yet
      (no "is_leader" key in /api/cluster/leader response)
```

The B1-T3 lease layer itself is wired (the binary's startup log
prints `lease store = redis @ ...`); only the **admin-API
projection** of leadership is missing. This is a follow-up:
either expose `is_leader` on `/api/cluster` directly, or add
the dedicated `/api/cluster/leader` route. Not a regression.

### Test 03 — rehydrate-readiness (B1-T5) — **PASS**

Stopped Redis, started node A, asserted `/healthz/ready` would
return 503 during the warm-up window, then started Redis and
asserted readiness flipped to 200 within
`state.reconcile.readiness_warm_ms` (5 s) + slack.

Result: **never observed 503** — the warm-up path completed in
a single iteration of the polling loop because Redis came back
faster than the 200 ms probe interval. The script logs this as
a WARN (host-speed artefact, not a contract violation) and
continues. Readiness flipped to 200 after Redis returned in
**< 1 s**.

The fact that the gate exists and is honoured is proven by the
node startup log:
`state backend rehydrate succeeded; readiness flipped to ready
elapsed_ms=5`. With a slower Redis the 503 window would have
been observable.

### Test 04 — partition-fallback (B1-T6) — **PASS**

Both nodes booted against shared Redis, both reported ready.
Stopped the Redis container (simulated partition). Both nodes
**kept serving the data plane** — confirms the
`ReconcilingBackend`'s fallthrough to local in-memory state on
`WafError::State`. Restarted Redis. Both nodes returned to
`/healthz/ready=200` within the heal window. The block-list
union check fired and reported "block lists converged across
nodes after heal" — both nodes' `/api/blocks` endpoints
returned identical sets.

## Cluster perf — k6 baseline against each node

Logs:
[`baseline-nodeA-2026-04-29.log`](./baseline-nodeA-2026-04-29.log),
[`baseline-nodeB-2026-04-29.log`](./baseline-nodeB-2026-04-29.log).

Same `baseline.js` used by the single-node perf re-run
(20 VUs / 15 s) but pointed at each cluster node in turn.
Both nodes share the same Redis primary so per-IP rate-limit
state is shared.

| Metric | Node A (port 8080) | Node B (port 8090) |
|---|---|---|
| `http_reqs` rate | 34 574 RPS | 34 529 RPS |
| `allow_latency_ms` median | 500 µs | 501 µs |
| `allow_latency_ms` p95 | 872 µs | 881 µs |
| `allow_latency_ms` p99 (visible from p95+max) | < 1 ms | < 1 ms |
| `allow_success` (count) | 9 999 / 518 624 | 9 999 / 517 964 |

**Reading the numbers**

- **Per-node throughput is identical within ~0.1 %.** B1-T1's
  `RedisBackend` doesn't add measurable latency vs the
  in-memory `aegis-redis` round-trip — both nodes see ~500 µs
  median allow-path latency (same as the single-node run).
- **`allow_success` ≈ 10 000 per node.** That's the per-IP
  rate-limit budget (10 000 in any 1-minute sliding window).
  **Both nodes admitted 10 000 each** — total ~20 000
  successes against the same source IP. If the rate-limit
  counter were truly cluster-shared, each node's window
  would have tightened on the other's writes; instead each
  node honoured its own 10 000 budget independently.
  - This is a **carry-over** worth investigating — B1-T1
    landed the `RedisBackend` for the *state* surface but the
    rate-limit *bucket* may have its own local counter that
    isn't routed through `StateBackend`. Test 01's idle-seconds
    signal (which IS shared) is from the RiskTracker view, a
    different code path.
  - Filed under "Carry-overs surfaced 2026-04-29 (cluster)" in
    [`Implement-Progress.md`](../../../../../Implement-Progress.md).

## HTTPS load — `tls-baseline.js`

Log:
[`tls-baseline-skip-2026-04-29.log`](./tls-baseline-skip-2026-04-29.log).

Ran with `WAF_TLS_TARGET` unset — k6 logged
`INFO: WAF_TLS_TARGET unset — skipping TLS baseline.` and
exited cleanly. Confirms the skip path works.

**Why we couldn't run the actual HTTPS baseline.** The
`config::TlsConfig.certificates: Vec<CertConfig>` schema is
*defined* in `aegis-core` but no listener-side consumer reads
it for the data plane today — the data-plane TLS path lives
behind the optional ACME flow (`acme:` block) or the
admin-listener-only resolver. To run the HTTPS load test we'd
need either:

1. Bring up the `pebble` ACME container from
   `deploy/docker-compose.test.yml` and add an `acme:` block
   to a config so the gateway issues + serves a real cert on
   `:8443`. The `tests/api/acme.sh` flow already proves
   Pebble round-trip works (F-T7), so this is achievable —
   it's just a longer setup than fits this run.
2. Wire the static `tls.certificates` list through to the
   data-plane listener. That's a code change, not a config
   change; **promote to a carry-over** so a future task adds
   the loader plumbing.

**HTTPS we could prove today.** The admin-listener TLS path
*is* exercised end-to-end by the existing
[`tests/api/tls.sh`](../../../../api/tls.sh) (TLS 1.0/1.1 reject,
1.2/1.3 succeed, HSTS + nosniff present) and by the new
[`tests/api/tls-ciphers.sh`](../../../../api/tls-ciphers.sh) cipher
negotiation script when the admin listener is configured with
TLS — neither of `waf.dev.yaml`, `waf.test.yaml`, or
`waf.cluster-{a,b}.yaml` enables admin TLS, so the cipher
script skips with INFO unless `AEGIS_ADMIN` points at a
TLS-enabled instance.

## Carry-overs surfaced by this run

1. **Leader-state admin endpoint missing.** Add `is_leader` to
   `/api/cluster` (or expose `/api/cluster/leader`). Without
   it, ops have no programmatic way to ask "is this the
   ACME / GitOps / threat-intel singleton today?".
   `tests/cluster/02-leader-failover.sh` will pick up the
   surface as soon as the field exists.
2. **Rate-limit bucket per-node despite shared state backend.**
   Each node admits 10 000 successes independently; the union
   should have been 10 000 across the cluster, not 20 000.
   Either:
   - Route the sliding-window counter through `StateBackend`
     so reads + writes hit Redis (current behaviour appears
     to be local-only).
   - OR document this as the intended behaviour (e.g.
     "per-node budget on top of cluster-shared block list"),
     which contradicts `docs/security/rate-limiting.md`.
3. **No data-plane TLS loader.** `tls.certificates` is parsed
   but unused for the data-plane listener. Either wire the
   static cert list through to `listener::tls`, or remove the
   field from the schema and direct ops to ACME.

## Reproducing

```sh
# Build with redis feature.
cargo build -p aegis-bin --release --features redis

# Reuse the existing aegis-redis container (host port 6379)
# instead of spinning up tests/cluster/_common.sh's default.
export AEGIS_REDIS_NAME=aegis-redis

# Run the cluster smoke track.
tests/cluster/run-all.sh

# Drive both nodes with k6 baseline (manually).
target/release/waf run --config config/waf.cluster-a.yaml &
target/release/waf run --config config/waf.cluster-b.yaml &
sleep 3
docker exec aegis-k6 k6 run -e DURATION=15s -e VUS=20 \
  -e WAF_TARGET=http://host.docker.internal:8080 /scripts/baseline.js
docker exec aegis-k6 k6 run -e DURATION=15s -e VUS=20 \
  -e WAF_TARGET=http://host.docker.internal:8090 /scripts/baseline.js
pkill -f 'target/release/waf'
```
