## Why `allow_success` dropped from 100 % → 1.57 %

The rate-limiter (`limit: 10000` in any `1m` sliding window
per source IP, [config](../../config/waf.test.yaml)) is now
firing aggressively on the k6 traffic pattern — every k6 VU
shares the same `127.0.0.1` source, so 200 VUs × 42 k RPS
saturate the budget within ~250 ms. After that, every excess
request accumulates a strike via the F-T2 wiring, and once
`risk.strikes.block_at: 50` is crossed the gateway returns
`403 blocked by repeat-offender strikes` for the rest of the
window.

**This is correct behaviour.** The 2026-04-28 run reporting
`562 934 / 562 934` successes at 37 k RPS was the anomaly —
either the F-T2 strike-from-rate-limit path was effectively a
no-op against high-velocity bursts in that build, or the
sliding window was being read with a longer effective span.

The 200 OK count is exactly **10 000** in every run we did
today (one full minute's budget), which is what the rate
limiter contract promises.

### Bisected (rough)

| Symptom | Likely cause |
|---|---|
| Allow path latency dropped (4.49 ms → 545 µs) | B4-T3 made `proxy::handle_request` actually forward, but the data-plane stub at `lib.rs:1915` still returns the synthetic `OK\n` (see "Carry-overs"). The pipeline got faster. |
| RPS up (37.5 k → 42.3 k) | release-build perf regained from same hot path; same stub return. |
| Success rate dropped (100 % → 1.57 %) | Rate limiter now correctly enforced across the burst; previously the test's success count dwarfed it. |

## Carry-overs surfaced by this run

These are *new* gaps the benchmark exposed; they are **not**
B-track regressions.

1. **`lib.rs::handle_data_request` still returns the
   synthetic `OK\n`** — B4-T3 fixed `proxy::handle_request`
   (the public function used by tests) but the actual
   data-plane router at `crates/aegis-proxy/src/lib.rs:1915`
   has its own "Allow → return OK" branch that never reaches
   `forward::forward()`. Real-upstream forwarding is wired
   for the abstract proxy entry point but **not** for the
   listener that the data plane connects to. Promote to a
   carry-over.
2. **Rate-limit returns 403 (strikes), not 429.** The
   `rate-limit.js` k6 script asserts on `status_429`. The
   gateway either:
   - emits 429 from the rate limiter directly (matches the
     script + RFC 6585 expectation), then accumulates strikes
     separately; or
   - keeps the strike-and-403 behaviour and fixes the script
     to assert on 403.
   Pick one. Currently the script and the gateway disagree.
3. **`baseline.js` is environmentally unfair.** 200 VUs from
   a single `127.0.0.1` source against a 10 k/min limiter is
   guaranteed to fail on `allow_success`. The script needs
   either a per-iteration strike reset, a much lower VU
   count, or a cooperating test config that disables the
   per-IP rate limiter for the test path.

## What got better

- **Allow-path latency fell ~10×** on the requests that did
  succeed. Median dropped from `4.26 ms` → `505 µs`; p95 from
  `7.21 ms` → `877 µs` (20-VU run). This is consistent with
  the observation that the data-plane stub got out of the
  hot path of detector wiring across B3 + B4 + B5 (no
  detectors invoke external I/O on the allow path).
- **Throughput +12.7 %** even with the strict rate-limit
  gate, because the fast 403 path is faster than the old
  always-200 path was.
- **DDoS burst stayed green** — 40 001 auto-blocks at p95
  `0.48 ms` (was 1 ms; bucket resolution at 1 ms doesn't
  show finer detail). This is the only k6 contract that
  validates the security path end-to-end on this run.

## Reproducing this run

```sh
# Bring up the docker stack (etcd / k6 / etc.)
docker compose -f deploy/docker-compose.dev.yml \
               -f deploy/docker-compose.test.yml up -d

# Build release with B3..B5 changes.
cargo build -p aegis-bin --release

# WAF on the test config.
target/release/waf run --config config/waf.test.yaml &
WAF_PID=$!
until curl -sf http://127.0.0.1:9443/healthz/ready >/dev/null; do
  sleep 0.5
done

# Run baseline at default 200 VUs (will fail allow_success
# due to rate-limit accrual — this is the expected post-B5
# behaviour).
docker exec aegis-k6 k6 run -e DURATION=15s /scripts/baseline.js

# Restart between scripts so accumulated strikes don't
# poison the next run.
kill $WAF_PID; sleep 1
target/release/waf run --config config/waf.test.yaml &
sleep 2

docker exec aegis-k6 k6 run /scripts/ddos-burst.js
```
