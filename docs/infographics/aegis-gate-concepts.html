00 — The big picture

System architecture

A single Rust binary that runs two planes. The data plane (public listeners) inspects and forwards traffic; the control plane (admin listener, loopback) runs the dashboard, API, and audit chain. The security invariant: the two planes bind distinct addresses and share nothing on the hot path except an ArcSwap<WafConfig> and the state-backend handle — so compromising one does not trivially reach the other.

Layer 1 · in-node

Tokio worker threads (multi-thread runtime, optional CPU affinity). Knob: runtime.workers / cpu_affinity.

Layer 2 · across nodes

N peers behind one VIP + an LB. Knob: node.id + Redis-shared rate-limit & leader lease.

Layer 3 · state

Redis-backed shared state — counters, leases, block lists. Knob: state.backend: redis.

How to read the rest of this guide. The data-plane stack above is the spine; each numbered section that follows zooms into one stage — the request lifecycle (§1), the gates and detectors inside the security pipeline (§2–§4), the challenge ladder (§5), DDoS (§6), the admission controller's load shedding (§7), and upstream mTLS (§8).
01 — Workflow

The request lifecycle

Every request is routed first, then runs a fixed pipeline of gates. Each gate either short-circuits the request (block, challenge, 429, 503) or adds score to a running risk total. After all gates run, the total is compared to the route's tier threshold: above the line it blocks, otherwise it forwards upstream.

Why the order matters. The access gate's four checks run before the detector chain, so a known-bad IP or a volumetric burst is rejected without spending CPU on regex inspection. The AI detector is deliberately last and only fires when no cheaper signature detector already matched.
02 — Request-flow gates

The four traffic gates

Four gates sit in the same architectural tier — before the detector chain. They all read the same shared cluster state and decide block-or-pass directly. They do not emit risk signals; they short-circuit the request. This is why a volumetric attacker is cheap to reject.

Rate-limit vs DDoS — the key distinction

Rate-limit enforces a steady per-request budget (token/leaky bucket) → 429 Too Many Requests with Retry-After.

DDoS handles a sustained burst → temporary block (sliding-window auto-block) → 403 for block_ttl_s seconds. The two are complementary — operators run both.

Never circuit_breaker

Per the interop contract, volumetric abuse from a single source may answer with rate_limit or block — never circuit_breaker. That action is reserved for upstream protection (the pool's own breaker), not source-rate management. The DDoS gate only ever emits block.

03 — Detection

Detector chain & the score ladder

Each detector is a pure function over the request. A hit emits a Signal {tag, score}. The per-request gate sums the signals and compares to the matched tier threshold. Read this chart top-down: a detector chip blocks a single request at any tier whose dashed line sits below it.

Per-request sum vs cumulative max. The per-request block gate sums all signals on this request. The separate cumulative IP bucket adds only max(signal) per request (rule SEC-M003) — so one request hitting three detectors doesn't triple-count against an IP's long-term reputation.
04 — Identity & reputation

Risk key & risk score

Risk is tracked per composite key, not per bare IP. Two browsers behind one NAT each carry their own bucket. Every request's score accrues to that bucket, decays over time, and drives the allow / challenge / block decision.

A · detector signals

Hardcoded per class (scores.rs). 25→100. The authoritative content signal.

B · identity / behaviour

YAML-tunable, default 10 each: bad ASN, bad JA4, failed auth, bot-unknown, repeat offender.

C · rules & special

Rule RaiseRisk(Δ), canary route → instant max, threat-intel feed hits.

DDoS stays per-IP by design. The Strike-block, cumulative-risk, and rate-limit buckets are per-RiskKey. The DDoS gate is the deliberate exception — volumetric protection must fire fast regardless of session or fingerprint.
05 — Friction, escalated

The challenge ladder

Instead of a hard block, suspicious-but-not-certain clients climb a ladder of increasing friction. The level is chosen from (risk_score, human_confidence, bot_class, tier) and is monotone — a client can't downgrade within the cookie TTL to fish for the cheapest level.

Challenges are opt-in per tier. Each tier carries a challenges_enabled toggle that defaults to false — so admin / payment / machine-only API tiers can run pure hard allow/block semantics (no PoW puzzle) without affecting other tiers.
06 — Volumetric defense

How DDoS protection works

A request-flow gate (not a detector) with two mechanisms: a per-IP burst gate that auto-blocks a single abuser, and an EWMA spike ticker that detects a fleet-wide surge. Both coordinate through the shared state backend, so a block on one node holds across the cluster. Secure by default: enabled: true, observe_only: false.

07 — Stay alive under pressure

Adaptive load shedding

Under saturation the WAF sheds its lowest-tier traffic first so CRITICAL routes keep serving. The concurrency ceiling is found automatically with the Gradient2 algorithm — no static limit that's wrong 99% of the time. Shed requests get an immediate 503 + Retry-After, with zero pipeline or upstream cost.

Worked model — same RPS, latency decides everything

Shedding is not triggered by RPS crossing a fixed number. It's triggered when RPS × latency-drift builds enough backlog that queue_wait exceeds 5 ms. So the same 200k RPS behaves completely differently depending on latency.

Full timeline. queue_wait 0.2ms → drift → 2ms → 4ms → 5ms (threshold) → shed starts + Retry-After:1 → AIMD shrinks limit → queue_wait falls to 3ms → AIMD grows +1/healthy-request → normal. The floor (1000) means even an over-aggressive shrink leaves enough capacity to absorb legitimate traffic and climb back fast.
Sizing. By Little's law, required concurrency ≈ RPS × inspection-latency. With sub-ms inspection a few hundred slots covers 10k RPS, so the limits leave headroom. Current config: initial_limit 5000 / min_limit 1000 (shipped profiles default 20000 / 2000; high-throughput 40000 / 4000). initial_limit doubles as the grow ceiling — the AIMD grow path never pushes past it. The high floor matters as much as the ceiling: a transient RTT blip can't shrink the limit far enough to shed healthy load before the gradient recovers.
Two things to know about the client-facing "waiting time." A shed request always gets Retry-After: 1 (1 second, fixed — not adaptive). Don't confuse that with the internal queue_wait signal above: that's the WAF's own run-queue dispatch delay measured per connection, and its 5 ms threshold is hardcoded in shed.rs, not configurable from YAML. The narrative doc docs/data-plane/adaptive-load-shedding.md still lists a "CPU-aware backstop" as design intent — not implemented; that's now stale — record_queue_wait is the implemented backstop.
08 — Zero Trust

Mutual TLS — both directions

"The cert" is ambiguous, so Aegis names the two directions explicitly. Downstream: the WAF is the server and verifies the client's cert. Upstream: the WAF is the client — it presents one shared fleet identity and verifies each backend's server cert. Both default off; enabling one never affects the other or any unrelated pool.

🔑 Crown-jewel key

The WAF client key can impersonate the whole fleet. It is never logged, never returned by any API/metric, never uploaded. Download/GET paths emit PUBLIC PEM only. In state mode the key stays a key_ref — only the public cert lives in the config plane. No envelope encryption (no hand-rolled crypto).

Fail closed, scoped

enabled + verify:true against an unverifiable backend fails that pool's dials with a clear reason — never falls back to trust-anything, never disturbs other pools. A source: state identity that's missing/corrupt aborts boot rather than dialing without client auth.

Hot rotation (P5)

A 5 s reconcile tick watches the config plane. Store a new cert and the fleet presents it within a tick — the next dial builds a fresh client while in-flight requests finish on the old one. Zero dropped connections, no restart. A deleted/corrupt record keeps the last-good identity.

Handshake-failure reasons (observability)

Per-pool, per-reason histogram on the Zero Trust page: untrusted_backend_cert san_mismatch cert_expired client_identity_error handshake_failed. Expiry shows as an amber badge inside 30 days.

Cost is paid once, not per request

Keep-alive is per pool, so the mTLS handshake is paid once per pooled connection. TLS 1.3 session resumption (tickets + 1.2 session IDs) lets a reconnect skip the full handshake. 0-RTT early data is off (replay risk). verify is a CA-chain check; the SAN gate is a cheap string compare.

Capability-gated. All cert mutation is audited, CSRF-gated, and behind admin.dashboard_auth.allow_ca_upload (off by default) — the upload UI only renders when the flag is on. This supersedes the old tls.client_auth and per-pool tls:{client_cert,…} shapes with no back-compat alias: migrate existing YAML.
