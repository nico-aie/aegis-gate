01 — The substrate

Foundations: language, runtime, and shape

These four choices are the hardest to reverse, so they carried the most scrutiny. Everything else is downstream of them. The through-line: a security appliance sits on the hot path of every request, so predictable tail latency and a small, auditable trust surface win over developer convenience.

ADR‑01

Rust, compiled to a single static binary

Decision: the whole gateway is one Rust workspace shipping ./waf — a single distroless-friendly binary, no runtime, no interpreter, no sidecar.
Context

The WAF is inline on every request. A GC pause or a memory-safety bug here is a production incident or a fresh attack surface — on the very box meant to stop attacks.

Why

Memory safety without a garbage collector gives predictable p99 with no stop-the-world pauses. A single ~70 MB binary deploys as a minimal distroless image, shrinking both the supply-chain and the runtime attack surface. Zero-cost abstractions keep the hot path allocation-light.

Trade-off accepted

Slower iteration and long compile times versus Go/Python; a smaller hiring pool. We treat the compile cost as bought-and-paid-for safety, and lean on the type system to make whole classes of bugs unrepresentable.

Rejected

Go — GC tail-latency jitter on the hot path. C/C++ — the performance is there but the memory-safety risk is exactly what a security product cannot carry. Envoy/nginx + Lua/WASM plugins — inheriting a large codebase we don't control and a plugin sandbox tax.

ADR‑02

Async on tokio + hyper 1.x, TLS on rustls

Decision: one multi-threaded tokio runtime, hyper 1.x for HTTP, rustls for TLS (with an optional aws-lc-rs FIPS provider).
Context

A WAF must hold tens of thousands of concurrent, mostly-idle connections (keep-alive, WebSocket, slow clients) while inspecting each one.

Why

Async I/O carries huge connection counts on a bounded thread pool — a thread-per-connection model would collapse. hyper 1.x is the mature, spec-correct HTTP core; rustls is memory-safe TLS with no OpenSSL CVE tail, and swaps to a FIPS-validated crypto provider by feature flag for regulated tenants.

Trade-off accepted

Async Rust is genuinely harder to write and reason about (lifetimes across .await, pinning). The tokio worker pool is fixed at boot — it cannot be resized live (see ADR-08), so worker-count changes need a restart.

Rejected

Thread-per-connection (simpler, but won't scale to WAF connection counts). OpenSSL (mature, but a recurring CVE surface and FFI risk we didn't want under the security boundary).

ADR‑03

Five-crate workspace, planes split at the crate boundary

Decision: aegis-core (shared traits/config) · aegis-proxy (data plane) · aegis-security (detectors/risk) · aegis-control (admin/audit) · aegis-bin (CLI wiring).
Why

The data-plane / control-plane isolation (ADR-04) is enforced by the compiler, not by convention: aegis-proxy cannot casually reach into admin internals because the dependency edge doesn't exist. Crate boundaries also parallelize builds and keep the hot-path crate free of admin-only dependencies.

Trade-off accepted

Shared types must be hoisted into aegis-core and trait-abstracted, which is more ceremony than a single crate. Cross-crate refactors touch more files.

Context

Feature flags (Redis, AI/ONNX, FIPS, OTel, cloud secrets) live per-crate, so a minimal single-node build pulls none of the heavy optional dependency trees.

Rejected

Single mega-crate — the original conceptual layout; abandoned because nothing stopped the data plane from importing admin code, weakening the isolation invariant.

ADR‑04

Two planes, one process — share nothing on the hot path

Decision: data plane and control plane bind distinct addresses (admin on loopback by default) and share only an ArcSwap<WafConfig> and the state handle.
Why

Blast-radius containment. A bug or compromise reached through a public listener does not trivially reach the dashboard, the audit chain, or the admin credentials — they're on a separate listener with their own auth stack. Keeping both in one process (rather than two services) avoids an inter-process trust boundary and keeps deployment to a single artifact.

Trade-off accepted

One process means a hard crash takes both planes down together (mitigated by HA replicas, ADR-09). The shared config seam is a deliberate, tiny, read-only coupling — we accept it rather than duplicate config state.

Context

The admin plane defaults to loopback + IP-allowlist at accept time, so it isn't publicly reachable unless an operator explicitly exposes it.

Rejected

Two separate services — cleaner isolation on paper, but adds an IPC channel, a second deploy unit, and a new authenticated surface between them.

02 — Truth, and where it lives

Configuration & state: one truth per data class

A WAF holds three very different kinds of data — a rarely-changing config, fast-moving shared counters, and an append-only audit trail. Forcing them into one store would compromise all three. So we split by data class, and each split is a deliberate consistency-vs-latency-vs-durability call.

ADR‑05

Lock-free hot reload via ArcSwap<WafConfig>

Decision: config compiles into one immutable WafConfig published through an atomic pointer swap; readers on the hot path never take a lock.
Why

Routes, rules, certs, secrets, and detector toggles all change at runtime with zero downtime and zero dropped connections. Each request grabs the current config with an atomic load — no mutex, no reader-writer contention under load. Crucially, an update is validated and compiled before the swap: a bad config is rejected and the running one is preserved, with a dashboard banner and an audit event.

Trade-off accepted

Granularity is the whole config — the swap replaces everything atomically, not a single key. Requests in flight during a swap may briefly observe the previous config (acceptable: each request is internally consistent). Subsystems that cache compiled state (route trie, rule tree, cert store) must subscribe to the reload event and rebuild their indices off the hot path.

Rejected

Mutex-guarded config — reader contention on every request. Restart-to-reload — drops connections and fails the zero-downtime requirement.

ADR‑06

State behind one StateBackend trait — in-memory default, Redis for clusters

Decision: all shared state (counters, risk, auto-blocks, nonces, leases) sits behind a single trait; the default build is in-memory, Redis is a feature-gated implementation, and a reconciling wrapper falls back to local on outage.
Why

A single-node dev box needs zero infrastructure — in-memory DashMap gives sub-microsecond ops and no Redis to run. The same binary scales out by pointing state.backend at Redis, which aggregates counters across the fleet (an attacker hitting node A then node B accumulates one risk score, not two). The Reconciling wrapper keeps the WAF serving during a Redis partition by falling back to local counters and reconciling on heal — split-brain-safe rather than fail-closed.

Trade-off accepted

Backend choice is boot-time only — cutting Redis over live without losing counters is hard enough that we made restart the safe default. Local fallback means counters can briefly diverge during a partition (we chose availability over strict global accuracy for rate-limit state).

Context

Redis is only a counter-sharing layer — never a config source. Everything in it is ephemeral and swept by the interop contract's /__waf_control/reset_state.

Rejected

Redis-always — forces infra on trivial deploys. Raft/embedded consensus for counters — far too heavy for volatile rate-limit data.

ADR‑06B

Config plane: a versioned Redis doc by default, optional etcd for consensus-grade clusters

Decision: fleet-wide config edits propagate as one versioned document activated by compare-and-set; the store sits behind a narrow ConfigBackend/ConfigWatch seam, so it is shared_state (Redis) by default and can be pointed at native etcd (config_plane.store: etcd, etcd_config feature) for Txn/Watch/Lease + Raft durability.
Why

A console edit on one node must converge on every peer and survive a leader failover. The CAS-versioned doc gives optimistic concurrency plus per-version rollback snapshots without standing up a second system for the common case. But Redis durability is best-effort — so clusters that need consensus-grade config durability and native watch/lease (instead of polling) can relocate only the config plane to etcd, whose cost is fine for low-write config data, while the ephemeral hot path (counters, cache, leases) stays on Redis. Because the plane lives behind the ConfigBackend seam, switching stores swaps an implementor, not the ~15 call sites; a one-shot waf migrate-config-plane handles the cutover with a documented rollback.

Trade-off accepted

Two config-plane backends to maintain and test. etcd is off by default so the shipped binary keeps its one-dependency (Redis-only) constraint — meaning etcd's stronger durability is opt-in and operators must run the migration tool to adopt it. Config and hot state now potentially live in two different stores, which operators must reason about.

Rejected / history

An earlier etcd config source (AEGIS_CONFIG_SOURCE=etcd) was removed in 2026-05-28 as redundant with file delivery + the Redis config plane, and a maintenance multiplier (every reload path had to be mirrored into it). The re-introduction (H2b) is deliberately scoped to the config plane store behind the ConfigBackend seam — not a parallel source. (The unrelated etcd service-discovery feature is just an upstream-pool member poller.)

ADR‑07

Dual audit sinks: a contract-locked file + a forensic hash chain

Decision: one minimal append-only JSONL file with a fixed schema (the benchmarked contract), running alongside a daily-rotated, SHA-256 hash-chained forensic log with optional SIEM fan-out.
Why

Two audiences, two shapes. The interop contract demands a single JSONL file with exactly 8 fields at a known path — so the benchmarker can correlate X-WAF-Request-Id to an audit line. Operators need something richer: tamper-evidence (hash = sha256(prev_hash ‖ event)), rotation, retention, and forwarding. Splitting them keeps the contract file rigid while the forensic chain evolves freely; both subscribe to one in-process audit bus, and the data plane never blocks on disk.

Trade-off accepted

Hash chains are per-node — there is no single cluster-global tamper-evident timeline out of the box. For multi-node forensics we lean on a central SIEM (Kafka/Splunk sink) as the source of truth rather than building cross-node witness exchange now.

Rejected

One do-everything sink — either too rigid for operators or too loose for the contract. Central DB sink (Postgres/ClickHouse) — deferred until a customer needs cluster-wide queries without an external SIEM.

03 — Three independent axes

Scaling: make each axis explicit, own none of the orchestration

A single box scales up only to one CPU and one NIC; past that you scale out, and any state shared between requests has to live somewhere both boxes see. We modeled that as three orthogonal layers and — importantly — drew a hard line around what the WAF refuses to own.

L1 · in-node

tokio workers + CPU affinity

Higher single-box throughput. Each request lives on one worker; CPU-bound detector chains benefit up to the logical-CPU count. Restart-only — tokio can't resize a live runtime, so the dashboard shows the sizing but offers no slider.

L2 · across nodes

HA cluster behind one VIP

Redundancy + horizontal capacity. Every node runs the full stack; an external LB spreads traffic. The console shows the roster and the one safe write — drain this node — but never add/remove-peer.

ADR‑08

Three-layer scaling model — and the WAF stays out of orchestration

Decision: scale on three explicit, independent axes (in-node workers · cross-node HA · shared Redis state); the WAF exposes visibility and a drain button, but topology (peer add/remove, autoscaling) belongs to the orchestrator.
Why

The three axes don't substitute for each other, so making them separate lets an operator pick a point on each independently (e.g. a 2-node cluster with one worker each and an in-memory backend is a valid low-complexity topology). Refusing to own topology keeps the WAF from re-implementing Kubernetes' HorizontalPodAutoscaler — and avoids the leader-election + quorum machinery that a peer-write API would require, which would itself become a split-brain risk.

Trade-off accepted

Worker resize and state-backend swap are both restart-only; there's no in-WAF autoscaler. Operators must run an orchestrator (k8s/Helm/Nomad) to get elasticity — we consider that the correct division of labor, not a gap.

Context

All three layers surface on one Scaling dashboard page so an operator can verify each without touching config files or redis-cli.

04 — The decision path

Security engine: cheap filters first, expensive judgment last

Every request runs an ordered pipeline where earlier, cheaper stages can short-circuit later, costlier ones — and the failure mode of each stage is resolved by the route's tier, centrally, so no individual stage has to know how important it is.

ADR‑09

Ordered, tiered pipeline with a central fail-mode contract

Decision: stages run cheapest-first with short-circuit; a route's tier (critical/high/medium/low) drives whether a failing stage fails closed (503) or fails open (skip + log), enforced by the orchestrator, not the stage.
Why

Ordering by cost means an obvious IP block or rate-limit never pays for AI inference. Centralizing the fail-mode decision means the contract is written once and can't be quietly violated by a new detector — a payments route (CRITICAL) is guaranteed fail-closed, while a marketing page keeps serving if a detector hiccups. This is expressed as a typed state machine threading a RequestContext and a growing Decisions struct.

Trade-off accepted

Fail-open on non-critical tiers means a degraded detector can let some traffic through un-inspected — a conscious availability-over-strictness choice for lower-value routes, with the tier system as the dial operators use to move a route up when that's unacceptable.

Rejected

Uniform fail-closed everywhere — turns any detector bug into a site-wide outage. Per-stage fail logic — scatters the security-critical policy across dozens of call sites where it drifts.

ADR‑10

Composite risk key with decay, not a per-IP counter

Decision: risk accumulates against RiskKey = (ip, device_fp?, session?), decays over time, and is judged against both a per-request block score and per-tier cumulative thresholds.
Why

A raw per-IP counter is both too coarse and too blunt: it punishes everyone behind a corporate NAT for one bad actor, and it never forgives. Adding device-fingerprint and session axes lets two sessions on one NAT'd IP be scored separately; time-decay gives trust recovery so a reformed client isn't blocked forever. Detectors, reputation, bot class, velocity, and threat-intel all feed one score, keeping the verdict explainable.

Trade-off accepted

More moving parts than a counter — decay rates and per-tier thresholds are extra knobs, and most of the cumulative tuning is intentionally hidden from the dashboard because the global defaults serve almost everyone. The multi-tenant tenant_id axis was retired when that feature was deprecated, simplifying the key.

Rejected

Flat per-IP block list — collateral damage behind NAT and no recovery path. Session-only keying — trivially defeated by dropping the cookie.

ADR‑11

AI detector as an operator-supplied ONNX model, feature-gated, observe→enforce

Decision: the ML detector runs a bring-your-own ONNX model via a Rust runtime (ort/tract), compiled in only with --features ai, and defaults to observing before it enforces.
Why

Signatures miss novel and obfuscated attacks; a learned classifier catches the long tail. Keeping the model operator-supplied and the whole subsystem behind a feature flag means the default build stays slim and doesn't ship a heavyweight ONNX runtime unless it's wanted. Running inference in-process in Rust keeps it on the sub-millisecond hot path (~0.5 ms p99). Observe-mode first lets operators measure accuracy on their own traffic before trusting it to block.

Trade-off accepted

The WAF doesn't ship a blessed model — operators must supply and version one, which is more setup. A probabilistic verdict needs the observe→enforce ramp and a fallback path, adding operational steps a pure-signature engine wouldn't.

Rejected

Bundled fixed model — bloats every build and ages badly. External inference service — a network hop on the hot path, blowing the latency budget.

ADR‑12

Adaptive load shedding (Gradient2), CRITICAL never shed

Decision: a per-listener admission controller derives its concurrency limit from live latency (L(t+1) = L(t) · RTT_min/RTT_now) — no static ceiling — and sheds by tier, dropping catch-all first and never shedding CRITICAL.
Why

A hand-tuned concurrency cap is wrong the moment hardware, upstreams, or traffic mix changes. A gradient controller finds the knee automatically from RTT, so the box protects itself under overload without an operator guessing a number. Shedding by tier means a traffic flood sheds low-value requests first and keeps auth/payment paths flowing; a shed response is an immediate 503 + Retry-After that costs no pipeline work and never touches an upstream.

Trade-off accepted

An adaptive controller is harder to reason about and test than a fixed limit, and can react to latency it doesn't cause (a slow upstream looks like overload). We accept that for the self-tuning benefit and back it with per-route soft/hard caps so one route can't starve others.

Rejected

Static concurrency limit — stale on every environment change. No shedding — lets a flood collapse the box and take critical traffic with it.

05 — Running it in anger

Operations & trust: deploy without dropping a request

The last cluster of decisions is about what happens after the code is correct — upgrades, credentials, compliance builds — where a WAF is judged on whether it can change safely while under live traffic.

ADR‑13

Zero-downtime ops: SO_REUSEPORT workers + hot binary reload via FD passing

Decision: N workers share a listener via SO_REUSEPORT; a new binary inherits the listening socket over SCM_RIGHTS while the old process drains; every config change is dry-run-validated before it swaps.
Why

Security patches must ship continuously, and an appliance on the request path can't take a maintenance window. Kernel-load-balanced workers plus FD hand-off let a new version accept connections while the old one finishes in-flight requests — a version upgrade with zero dropped connections. SIGTERM and /admin/drain flip readiness to 503 so external LBs bleed traffic away within one probe interval; readiness-probe failure rolls the hot restart back.

Trade-off accepted

The FD-passing and SO_REUSEPORT mechanics are Linux-first, and the graceful-restart path is genuinely intricate to implement and test. That complexity is the price of not having a maintenance window.

Rejected

Stop-and-start deploys — drop connections, fail the SLO. Blue/green at the LB only — works, but doubles fleet cost and still needs the drain contract we built anyway.

ADR‑14

Single hardened admin principal now; RBAC/SSO deferred (not skipped)

Decision: v1 ships one admin identity gated by argon2id + HMAC session + CSRF + optional TOTP + IP-allowlist + optional mTLS; multi-user RBAC and OIDC SSO are an explicitly sequenced follow-on, not an afterthought.
Why

The crypto and session foundation that matters for a secure single admin — modern password hashing, tamper-resistant sessions, CSRF, second factor, network-level gating — is fully in place today. That covers the threat model for a small operator team and let us ship a defensible product without first building an identity provider. The roadmap treats multi-user accounts → RBAC → per-user audit → OIDC SSO as a staged track, with self-service hardening (kill committed defaults, wire dormant endpoints) as the standalone first step.

Trade-off accepted

One principal means no per-operator accountability (every audit action reads admin) and no least privilege (every session is full-scope) until the RBAC track lands. We accepted that gap consciously and wrote it down rather than half-building an auth system under time pressure.

Rejected

Full RBAC/SSO in v1 — large, and everything keys off roles, so rushing it risks a privilege-escalation bug in the security console itself. Delegate to a reverse proxy for auth — leaves the admin API unprotected if that proxy is misconfigured.

ADR‑15

Pay-for-what-you-use builds via Cargo feature flags

Decision: Redis, AI/ONNX, FIPS crypto, OTel, Kafka, HTTP/3, HSM, cloud-secret providers, and GeoIP are all optional features — the default build compiles none of their dependency trees.
Why

Different deployments have opposite needs: an air-gapped single node wants the smallest possible binary and attack surface; a regulated tenant needs a FIPS-validated crypto provider; a cloud fleet wants Redis, OTel, and cloud secret managers. Feature flags let one codebase produce all of them without carrying every dependency into every image — smaller binaries, faster builds, fewer CVEs to track per deployment. A FIPS build, for instance, enforces a primitive allowlist at load time and refuses non-FIPS crypto.

Trade-off accepted

A combinatorial feature matrix is more to test in CI, and a capability's presence now depends on how the binary was built — so docs and error messages must be explicit about "compile with --features x." We accept the build-matrix cost for the deployment flexibility.

Rejected

One fat build with everything on — bloats every image, forces heavy deps (ONNX runtime, Kafka) onto deployments that never use them, and widens the supply chain for all.

ADR‑16

Built to a benchmarked interop contract, with named production profiles

Decision: the WAF conforms to a versioned interop contract (X-WAF-* headers, /__waf_control/*, a fixed audit schema) and ships three tuned profiles — prod-balanced, prod-strict, prod-high-throughput.
Why

An external contract makes behavior testable and comparable rather than a matter of opinion — every response carries the action, reason, and a request-id that ties back to an audit line, and a reset endpoint gives repeatable benchmark runs. Named profiles encode the security-vs-latency trade-off as a supported choice with measured numbers (balanced ≈ 1.9 ms median / 4.5 ms p99), so operators start from a known-good point instead of hand-assembling config.

Trade-off accepted

Conforming to an external wire shape constrains internal freedom — header names, endpoints, and the audit file's schema are locked and must be preserved across refactors. Profiles must be kept honest with re-measured numbers as the engine changes.

Context

The contract-locked audit file stays deliberately minimal (ADR-07) precisely so the richer forensic chain can evolve without breaking the benchmark.
